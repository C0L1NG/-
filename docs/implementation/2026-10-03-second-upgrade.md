# 第二轮审查整改记录

范围：依据 `docs/reviews/2026-10-03-second-review.md` 修复当前项目。原审查报告及其 JSON 是修复前证据，未改写成修复后的结果。历史 probes 用于理解原缺陷；当前验收使用新的回归测试。

## 已实施的修改

- **R2-01：退款后付款资格。** start 在提现单与钱包行锁内检查债务及冻结资金；退款欠款阻止领取付款。付款详情与表单展示风险。处理中发生退款仍先核查真实渠道结果，实际已付出则照实确认，保留债务。
- **R2-02：两端退出竞态。** 会话代次在退出时失效，迟到的 wx.login、登录响应、401 和请求重放均不能复活会话；老板同时移除登录方式。主动再次登录允许开启新会话，旧响应不能覆盖新令牌。
- **R2-03：网关限流。** BFF 签名传递匿名浏览器上下文，Python 不信任任意转发 IP；来源与账户双范围限流存入 PostgreSQL，多 API 实例共享。增加真实 Next → FastAPI → PostgreSQL 联调，并加入 CI 步骤。
- **R2-04：支付事件恢复。** 验签证据独立提交到 payment_inbox，内容不可改；资金事务失败后保留状态、次数与错误标识。恢复 worker、CLI 与老板分页恢复入口可重新处理原通知，资金更新与成功处理事件仍原子提交。
- **R2-05：业务对账。** 同一快照内分开核对钱包总量、增量规则、提现状态与冻结/付款/释放流水、审批最新状态、分润归属及比例、退款原始分配和孤立业务引用。移除逐退款查询造成的额外往返。
- **R2-06：驳回字段。** rejection_reason 与 failure_reference 分别保存；payout_reference 只用于成功付款且继续全局唯一。相同原因能驳回不同提现，旧 reject transferReference 保留兼容。表单分开填写原因和渠道凭据。
- **R2-07：报表快照。** 受保护 GET 先验证 JWT，再在数据库身份查询前开启只读 REPEATABLE READ；大盘金额与计数、分页总量与列表来自同一快照。并发结算回归验证内部一致。
- **R2-08：CSV 类型。** 可信 Decimal 负数保留数值，不再附加单引号；昵称、订单号等外部文本继续防公式注入。跨月退款测试直接解析输出，无 lstrip 补救。
- **R2-09：经办人与审计。** 领取、确认、驳回有 claimant、版本及追加审批记录；其他管理员操作返回冲突，相同经办人的同内容重试保持幂等。未知渠道状态不会自动释放或转交。
- **R2-10：索引。** 新增 user_id / kind / created_at / id 复合索引及退款、平台收益时间索引。50,001 行合成资金流水中，目标代理的退款查询使用新索引。此结果不代表生产容量或延迟测量。

额外完成：资金写接口及登录/网页码交换补成功响应模型；生成 TypeScript/OpenAPI 已同步；审核列表中文状态与昵称，账户默认脱敏、按需复制，展示经办人和历史；跨 BFF/API 共享请求标识；恢复任务周期对账并输出积压/异常日志；准备和存活检查包含新增表/字段。

## 迁移与兼容

新增 `prisma/migrations/20261003010000_second_review_fixes/migration.sql`，保留旧迁移历史，SQLAlchemy 与 Prisma 新字段一致。旧已驳回单的 payout_reference 移到 rejection_reason，旧 processing/paid 经办人从 reviewed_by 继承。已有关联和原二级分润规则保留。新增收件箱不伪造旧事件；历史缺乏可验证资料的单据仍需人工核查。

3. 本轮未执行正式库迁移、公开发布、远程 CI、生产恢复或吞吐压测。本地 Python 3.14.3，CI 配置为 3.12，远程结果仍需执行确认。
4. 真实支付原生验签、主动查单、渠道付款幂等、银行保管服务和两端微信真机仍需凭实际渠道配置验收。系统目前记录人工核对结果，不会自动银行/微信转账。
5. 经办人领取不会自动过期或换人，避免未知外部付款被重复执行。现有处理人应先查清渠道结果；人员离职或旧处理中单无经办人时，仍需受控人工处理，不能直接再次付款。
