# 第三轮全面检查与界面改造

日期：2026-10-04。对象：当前工作树，包含前两轮尚未提交的整改。本轮发现与修复应以本文和对应文件为准，不能用整个 Git diff 代表本轮新增工作。

## 结论

**原 UI 的主要问题是信息优先级失衡：深绿色大卡、胶囊和宣传眉题重复堆叠，余额、待办与流水反而缺乏区别。** 单纯继续换颜色，无法解决这个问题。本轮已重做代理资产首页、老板资金总览和桌面工作区，以中性黑白、细分隔线、白色主操作和正负金额状态区分组织界面。

财务核心已有可继续维护的基础。Decimal 分位计算、订单归属快照、行锁、原子钱包更新、退款冲正、经办人认领和身份过滤应继续保留。本轮没有发现需要推翻这些机制的证据。但真实付款渠道、外部告警和微信真机闭环仍未验收，不能把演示页面或测试通过当成真实资金系统上线结论。

- 阅读资金结算、钱包、支付事件、退款、提现、RBAC、绑定、报表、恢复 worker、Web BFF、共享前端、原生工程和 CI。
- 独立 PostgreSQL 16 测试库运行现行后端：**79 通过、0 跳过**。未访问生产数据库。
- 旧 TypeScript 对照测试：**20 通过**。前端工具和小程序测试：**27 通过**，包含本轮金额显隐与周期排名回归。
- 真实 Next → FastAPI → PostgreSQL 集成验证：登录隔离限流、Cookie 登录、后台恢复首轮执行、正常退出、错误 Origin 拒绝及后端断开时本地退出。[机器结果](review3-bff-evidence.json)。
- 正式 Web 与静态展示版生产构建通过；TypeScript、Prettier、Ruff、Pydantic 类型及 OpenAPI 契约检查通过；41 个共享文件同步检查通过。
- 浏览器检查代理 375px / 430px、老板移动 430px、老板桌面 1280px / 1440px。覆盖工作区切换、二级展开、代理详情、审计筛选/导出、资金待办跳转、金额隐藏与退款详情、浅色主题和演示提现提示。
- 没有进行完整渗透测试、生产压力测试、灾备恢复演练、真实渠道付款或微信真机验收。小程序 JavaScript 模拟不能代替微信渲染与系统权限验收。

## 本轮已修复

### R3-01 · P1：Web 退出依赖后端成功，故障时可能保留会话 Cookie

原代理转发在上游异常时返回错误，清理 Cookie 的成功路径没有覆盖该情况；老板端也共用转发逻辑。结果是用户点击退出后，本地凭证仍可能留在浏览器中。

现在先验证 Origin，再保证退出路径清除对应角色的 HttpOnly Cookie。远端撤销是否成功通过 `sessionRevoked` 明确返回。后端不可用时只保证当前浏览器退出，不宣称其它设备或已复制令牌已经撤销。

真实集成测试先登录，再停止临时 FastAPI 服务，两端退出均清掉 Cookie，后续受保护请求返回 401；错误 Origin 请求保持 403，不能借退出接口绕过同源校验。实现：[auth-proxy.ts](../../web/lib/auth-proxy.ts)，回归：[check_bff_integration.py](../../python_backend/tools/check_bff_integration.py)。

### R3-02 · P2：老板手机端点击代理名字无可见详情

共享团队组件更新了选中状态，但详情区域只在桌面渲染。已为移动端添加可关闭的详情面板，展示钱包、累计净收益、团队人数和所选周期 GMV；保留键盘焦点与关闭行为。已在 430px 浏览器点击验证。[admin-network.tsx](../../web/components/admin-network.tsx)。

### R3-03 · P2：原生代理小程序金额隐藏仅作用于首页

原生首页的 `hidden` 是本页状态，切到进展、明细、团队和提现页仍会显示金额。已加入共享持久化偏好，各财务页面 `onShow` 同步，模板遮蔽金额，收益构成条在隐藏时收起。存储失败有明确反馈。[privacy.js](../../miniprogram/services/privacy.js)、[回归测试](../../miniprogram/tests/privacy.test.cjs)。Web 列表与退款详情的隐藏行为也已浏览器复核。

### R3-04 · P2：演示团队排行榜与所选周期不一致

浏览器观察到本月平台贡献 297,000 元的团队排在 252,000 元之后。原因是演示节点使用固定数组顺序。现按当前周期的团队平台贡献排序，金额比较使用整数分，避免 Number 精度问题；页面明确显示本月或全周期。该发现影响演示数据排序，正式查询已有服务端贡献排序。[admin-demo-data.ts](../../web/lib/admin-demo-data.ts)、[回归测试](../../scripts/tests/finance-ui.test.mjs)。

### R3-05 · P2：操作层级混乱、部分输入仍依赖浏览器弹窗

老板桌面原页面把资金、团队、审计和操作混在长页内。现拆成四个可切换工作区，待办可直接定位资金处理状态。账户核验改为带校验、等待态和错误提示的页面内表单。审计采用紧凑可展开记录，保留完整金额、退款状态及日期筛选。

### R3-06 · P2：中止的旧读取仍存在覆盖新页面的路径

概览、首页与团队读取补上响应落地前的中止检查，使快速切换身份、周期或页面时的旧请求不再更新已失效状态。原有分页版本保护继续保留。本轮未修改 API 路径、分润比例或数据库结构。

## 仍需改进的事项

### P1 · 真实资金运营的外部链路仍需交付

当前回调面向可信网关签名事件；实际支付通道的验签适配、退款发起、渠道查单和付款凭据核验需要按商户渠道验收。系统不会自动向银行或微信转账。下一步应拿选定渠道的测试商户贯穿“付款结果未知 → 查单 → 重复通知 → 退款 → 追偿”的演练。此项是已知交付边界，不是本轮证明发生了丢款。

### P2 · 告警仍停留在日志，缺少送达与认领闭环

[worker.py](../../python_backend/app/worker.py) 能恢复事件、定期对账并记录异常数量，但没有实际接入告警渠道、确认状态与升级策略。进程活着不代表有人处理差错。应定义对账不平、积压超时、重试耗尽的告警和负责人，并验证故障通知真正送达。

### P2 · 客户购买推广与代理招募尚未形成完整双链路

目前邀请码是代理入驻入口；严格二级规则下二级代理不能再招募下级。客户购买推广需要独立落地页、客户归因和订单创建链路。当前 UI 已准确说明未开通，不能把取消层级限制当作获客功能。后续应先确定商品与成交入口，再实现归因。

### P2 · 多端交付与变更管理成本仍高

Web、两个原生小程序、展示入口、旧 TS 对照代码仍需要分别维护。共享 Web 组件有同步门禁，但展示入口模板只在缺失时生成，已有入口修改仍需显式同步；原生提现和老板网页桥接也与 Web 存在能力差异。应建立逐端能力清单，明确展示入口所有权和废弃代码计划，并补微信真机回归。

此外，`admin-dashboard.tsx` 约 558 行、`agent-profile.tsx` 约 485 行，仍同时协调数据、状态和页面布局。后续可提取概览数据读取与个人中心邀请功能；不建议为拆文件增加一层无实际职责的抽象。当前工作树变更多且未提交，建议按资金、认证、UI 分批形成可追溯版本。

### P2 · 大数据量容量尚未验收

平台钱包的单行更新会串行化结算，网络报表包含全量聚合；后端 CSV 虽采用流式一致快照，前端 [admin-export.ts](../../web/lib/admin-export.ts) 仍把结果收成 Blob。大文件下载会占用浏览器内存，长导出也会延长数据库快照生命周期。应以业务峰值和目标数据量做压测，必要时引入异步导出任务与限额。目前没有证据说明现有数据规模已经超限。

## 后续顺序

1. 完成选定支付渠道与微信真机的端到端验收。
2. 把恢复和对账日志接入可送达、可认领的告警。
3. 实现客户成交推广归因，补齐多端能力清单。
4. 用真实目标负载验证锁竞争、团队查询与大批量导出，再决定是否拆服务。

**锐评：资金内核已经比演示工程扎实，界面现在也有明确的金融工作台层级。项目最欠缺的依然是可运营的外部闭环与可追溯交付。下一轮继续整页换皮，收益会明显低于把支付、告警和真机路径验收到位。**
