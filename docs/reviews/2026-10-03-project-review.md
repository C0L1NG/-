# 分润平台代码审查 · 2026-10-03

> 后续整改见 [2026-10-03 升级记录](../implementation/2026-10-03-upgrade.md)。本报告保留整改前的审查证据。

## 结论

这是一个有分润结算内核的高保真产品原型。界面与正常路径的完成度，明显领先于真实资金业务、登录接入、异常恢复和交付复现能力。可以演示产品方向；现有证据不足以支持直接上线收款运营。

当前应优先完成一条真实业务闭环，而不是继续扩大页面数量。前一轮结构整理有价值，但不代表生产问题已经关闭。本次仅审查并保存报告，没有修改应用逻辑。

## 审查范围与证据边界

- 检查 Python 后端、旧 TypeScript 后端、Prisma 模型与迁移、Web 前端、展示站、小程序、测试和 CI。
- Python 测试：26 通过，2 跳过；跳过的是需要真实 PostgreSQL 的测试。
- 旧 TypeScript 测试：20 通过。本机已有生成文件时，类型检查通过。
- Web 和展示站的生产构建均通过；生成的接口类型校验通过。
- 另做了数据库 URL、干净检出类型检查、小程序生命周期与分页、展示站同步、微信错误响应的针对性探测，见各项发现。
- 未运行真实 PostgreSQL 并发事务、支付通道、微信真机、线上部署或远程 GitHub CI。本机 Docker 服务不可用。编译成功不能替代这些验证。

## P1：上线前必须解决

### 1. 资金链路没有闭环

**性质：源码确认的功能缺口。**

`python_backend/app/commission.py:52` 有可靠性措施较好的结算函数，但仓库生产入口没有调用它。现有 API 没有订单支付验签回调、提现申请执行、退款冲正等完整入口。README 将支付后调用留给外部业务接入。

`web/components/agent-home.tsx` 的提现、`agent-profile.tsx` 的收款账户绑定、`admin-mobile-home.tsx` 的商户提现仍是待接入提示。数据库有退款/冲正状态枚举，但缺少对应业务处理和可追踪的余额变化记录。

**影响：**页面可以显示佣金，平台尚不能完整回答“钱如何可靠地进入、冻结、付出、退回，以及每一步失败如何恢复”。把状态改为退款，并不会自动撤销已经入账的佣金。

**建议：**接通验签支付事件、事件幂等记录、结算任务重试、提现冻结与解冻、退款冲正和对账。余额调整必须有方向、原因、关联业务单及唯一幂等键，避免直接手工改余额。用一笔真实测试订单贯穿完整流程验收。

### 2. Web 登录和会话恢复仍依赖未交付的接入

**性质：源码确认的接入缺口。**

`web/lib/proxy.ts` 要求 agent/admin Cookie，但 Web 没有相应登录签发流程。Python 提供微信代理登录；管理员登录依赖 README 所述的外部登录服务，仓库没有交付这段集成。401 页面只能提示或重试。

`python_backend/app/security.py` 的代理 Token 有两小时有效期；`miniprogram/services/api.js` 没有 401 续登机制，登录主要发生在启动时。长期保留在后台的小程序会遇到过期后无法自恢复的问题。

**建议：**明确管理员身份来源、接通 Cookie 签发，完成代理登录失效恢复、账号停用与会话撤销策略。现有鉴权对签名、角色和数据范围的校验值得保留；缺口在完整的身份生命周期。

### 3. Python 数据库 URL 适配不能保证直接替换旧配置

**性质：已复现。证据：`python_backend/app/db.py:9`。**

转换数据库驱动时只移除了 `schema`，其余 URL 参数继续传给 asyncpg。分别探测以下参数，均在建立连接前报错：

- `sslmode=require` → `TypeError: connect() got an unexpected keyword argument 'sslmode'`
- `connection_limit=5` → 同类参数错误。
- `pool_timeout=10` → 同类参数错误。

**影响：**使用这些旧 Prisma/libpq 参数的部署不能直接更换后端运行，尤其容易在正式环境才暴露。

**建议：**显式转换 SSL 与连接池参数，未知参数在启动时给出明确诊断；增加旧连接串兼容测试。无需继续宣称所有旧配置均能热插拔。

### 4. 干净检出的交付验证不可靠

**性质：本地干净检出复现；未实际执行远程 CI。**

`.github/workflows/checks.yml:46` 安装后直接做类型检查，但旧后端导入被 Git 忽略的 `generated/prisma/client.js`。工作流没有显式生成 Prisma 客户端的步骤，也没有为生成提供数据库 URL 配置。

将 HEAD 导出到临时目录，复用本机已安装依赖后运行类型检查，出现多处 TS2307 找不到 Prisma 生成文件；当前工作目录因已有生成产物而通过。该实验没有进行全新的网络依赖安装，不能等同于远程 CI 的运行结果，但已确认检查依赖未提交的本地产物。

**建议：**明确执行 Prisma 生成并提供测试配置，或完成旧后端退役后退出旧代码检查；加入从干净检出开始的迁移、构建、启动冒烟验证。CI 还应覆盖正式 Web 构建及真实数据库测试，不能只看本机绿色结果。

### 5. 扫码邀请存在生命周期缺陷

**性质：源码与 Node VM 模拟均确认。证据：`miniprogram/app.js:5`。**

`app.ready` 只等待登录，没有等待 `bindParent`。模拟中 ready 已完成，但绑定仍未结束。页面可能先按未绑定账户加载收益比例。代码只处理 `onLaunch`，没有处理小程序已运行时再次扫码进入的 `onShow` 场景。

后端对三级绑定有正确拒绝，但前端仍向二级代理提供完整邀请入口。微信登录先建立根代理；绑定失败后只弹提示，会保留未绑定身份，业务结果不够明确。

**建议：**把登录和首绑纳入明确的就绪状态；冷启动、热启动都处理入口参数；给“绑定成功、已有上级、禁止三级、邀请失效”分别设计结果。二级代理能推广商品还是能招募代理，需要在功能和文案中明确。

### 6. 历史订单的受益人取决于结算时的团队关系

**性质：源码确认的时点依赖；需要业务规则决定。**

`commission.py:74` 读取结算时的 `parent_id`。订单没有父级快照或分润规则版本；`binding.py:29` 允许没有团队的根代理首次绑定上级，并不检查既有订单。

例：代理无上级时订单已支付，尚未结算；随后首次绑定上级；结算时由原先预期的 70% 变成 49%/21%。现有锁能保护结算事务执行期间的关系，不能确定历史归属。已经结算的流水不会因此自动被改写。

**建议：**先确定以创建订单、支付成功还是结算时作为归属时点。若要求支付时确定受益人，应保存不可变归属快照与规则版本；也可以明确禁止有财务活动后首次绑定。对边界场景增加集成测试。

## P2：会造成误读、遗漏或规模问题

### 7. 小程序超过 100 条的数据不会显示

**性质：已复现。**

`miniprogram/pages/ledger/index.js:2` 与 `pages/team/index.js:2` 固定只请求第一页 100 条，没有翻页处理。用 `total=101, totalPages=2` 模拟，两个页面均只发一次请求并展示 100 条。

`web/components/agent-progress.tsx:42` 同样只取 100 名成员再本地排序，所谓贡献领先成员仅来自这部分样本。

**建议：**流水与团队实现完整分页；贡献排名交给后端按全量数据计算，不能用提高页面上限代替。

### 8. 财务指标的统计时点没有统一

**性质：源码确认；部分定义已在 README 说明，但产品标签不够明确。**

- `routers/agent.py:48` 的“今日预计”只统计 UTC 今天创建、已支付、未结算的订单。订单一旦结算，这部分就消失；昨天创建、今天支付的订单也不计入。
- `routers/admin.py:25` 平台收益按订单创建时间筛选；代理月度明细按佣金流水时间筛选。跨月订单会出现在不同月份。
- 管理端 GMV 仅统计 PAID；收益累加已有流水。如果未来只更新退款状态而没有冲正，成交与收益口径会不一致。

**建议：**定义创建、支付、结算、退款时间与业务时区，分清成交额、净成交额、已结算收益和待结算预计。API 和界面共同使用这些定义。

### 9. 金融统计和对账导出过度依赖前端抓取全量记录

**性质：源码确认的设计问题；未做负载基准测试。**

`agent-progress.tsx:29` 和小程序首页循环下载整个月流水后求和；`queries/admin_tree.py` 返回全网关系树；管理员移动端定时加载整棵树；`web/lib/admin-export.ts:15` 下载全部历史订单到浏览器再拼 CSV。

除耗时和内存外，审计接口使用按时间倒序的 offset 分页。导出过程中有新订单插入，页边界会移动，可能重复或漏取记录。对账导出需要稳定的数据范围。

**建议：**统计走数据库聚合；树按一级和子节点分批加载；导出使用固定截止时间和稳定游标，或数据库快照，数据大时用后台导出任务。无需提前拆微服务。

### 10. 接口契约只覆盖了部分成功路径

**性质：错误响应已复现。**

模拟微信服务抛出当前代码使用的 `RuntimeError`，`/api/auth/wechat/login` 返回 `500 text/plain: Internal Server Error`。`factory.py:36` 没有统一处理上游异常；旧服务的错误 JSON 行为无法由当前响应类型生成器保障。

生成的 TypeScript 类型有帮助，但只覆盖选定的响应模型；请求参数、HTTP 状态、错误体和运行时校验并未因此自动一致。前端泛型类型声明也不会验证真实 JSON。

**建议：**统一错误响应，对微信拒绝/超时作明确映射，并为请求、成功响应、失败响应建立契约测试。后续可从 OpenAPI 生成完整调用客户端。

### 11. 展示站复制同步仍会产生漂移

**性质：已复现。证据：`scripts/sync-showcase.mjs:24`。**

- 给展示站单独增加遗留组件，`--check` 仍返回成功，因为只枚举源目录。
- 给 Web 增加嵌套组件目录，目标目录不存在时，同步报 `ENOENT`，脚本不创建父目录。

根仓库忽略 `showcase-site`；展示站是独立 Git 仓库，本地无 remote。根仓库检出本身不能还原整个展示工程，复制脚本也未纳入 CI。独立站点托管可能另有历史，但不能替代可复现的源码交付。

**建议：**共享 UI 包，分别提供正式版与演示版的数据适配器和应用入口。若暂留复制方案，应支持目录、资产、删除同步、文件清单和 CI 检查，并明确展示站源码的备份与发布来源。

### 12. 微信小程序和手机网页已出现产品分叉

**性质：源码确认。**

原生 `miniprogram/app.json` 仍是首页/推广/团队/明细及浅色配置；新深色首页/进展/明细/我的主要存在于 Web。小程序仍使用 `touristappid` 和示例 API 地址。老板移动端是 H5 页面，仓库没有完整的管理员小程序登录桥接。

**建议：**明确 H5、原生小程序各自的交付范围和验收标准；实现真机登录、扫码、太阳码生成、海报保存和后台恢复。手机尺寸的页面预览不能证明这些功能已完成。

## P3：维护和体验质量

- 大量一行 JSX 和超小字号让审查、修改与阅读困难，应统一格式化并按业务职责拆组件。
- 弹层需要键盘焦点、Escape 关闭、焦点恢复等无障碍支持；本次未进行完整辅助技术测试。
- 请求失败后不应把默认零金额或空列表呈现成真实业务结果；应展示明确的不可用状态，并允许单模块重试。
- 缺少足够的生产健康检查、关联请求日志、结算失败告警及对账监控证据；依赖版本锁定和部署文档还需完善。
- 如果将来真的服务多个独立商户，目前单平台 admin/agent 模型需要增加租户隔离。当前没有确认这个需求，不建议仅因名称叫 SaaS 就立即引入多租户复杂度。

## 应当保留的基础

- Decimal 与数据库定点金额类型，采用余数分配以保持每笔分润金额守恒。
- 订单行锁、事务内日志与状态更新、钱包原子增量，以及稳定的钱包更新顺序。
- 分润唯一约束、团队层级约束和数据库触发器，不应在 ORM 重构时遗漏。
- JWT 验证和按当前登录代理筛选查询。本次检查没有确认可直接通过传入其他代理 ID 绕过权限的缺陷；这不等同于完整渗透测试结论。
- Pydantic 类型生成、现有金额测试及真实 PostgreSQL 测试脚手架。

## 建议的改进顺序与验收条件

### 第一阶段：可靠启动、可靠登录

修复连接串兼容与干净检出构建；接通管理员及代理身份流程；统一错误响应；真实 PostgreSQL 测试必须实际运行。验收：新环境按文档可启动，管理员与代理分别登录，跨角色访问被拒，过期会话可恢复。

### 第二阶段：完整资金闭环

确定归属快照与时间口径，接通支付、结算重试、提现和退款冲正。验收：重复回调不重复入账、并发订单总额正确、中途异常事务回滚、提现失败恢复冻结、退款后账目可解释。

### 第三阶段：正确的数据与真实小程序

修复扫码时序、热启动入口、分页与排名；服务端提供聚合和稳定导出；完成微信真机验收。验收：第 101 条数据可见，跨月账目口径一致，持续新订单下导出无重复遗漏。

### 第四阶段：统一维护与发布

共享展示 UI 和正式 UI，明确旧后端退役范围，完善发布、监控、格式化与交互。当前采用模块化单体足够，不建议用微服务重写掩盖尚未完成的业务流程。

**最终判断：该项目值得继续做，但优先级必须从页面扩张转向业务完整性、金额可追溯性和可重复交付。**
