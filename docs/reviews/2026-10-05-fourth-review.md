# 第四轮系统审查与优化路线

日期：2026-10-05。审查基线：Git `0a4342e`，开始审查时工作区干净。

本轮交付是检查结果、复现证据、整改方案和设计提案。未修复生产业务代码、未更换现有页面、未提交或发布。

## 结论

项目已具备可继续迭代的资金内核，但还不能仅凭既有测试全绿就判断关键业务边界已经覆盖。此次新增探针确认了两项 P1：**退款事件乱序时，已知退款仍可能被继续放款；退出与网页登录票据创建并发时，已撤销会话可能换到新凭证。** 本文共列出 2 项 P1、5 项 P2、2 项 P3；区分已运行复现与代码路径证据。

UI 的问题也仍然存在。上一轮改造改善了配色和分区，但大金额、分隔线和固定规则仍占据过多注意力；状态反馈与阅读上下文也不够稳定。设计应该围绕“老板现在需要处理什么”和“代理现在真正能用多少钱”组织。

不建议继续整仓推翻、加一轮渐变，或为了架构感拆微服务。保留已有效的事务、分位计算、归属快照和权限边界，补齐事件一致性、凭证撤销和入账对账，再统一页面数据状态与视觉语言。

## 新确认的问题

### R4-01 · P1：已接收的退款事实未阻断后到支付释放佣金

**位置：**[payments.py:197](../../python_backend/app/payments.py#L197)、[payments.py:159](../../python_backend/app/payments.py#L159)、[withdrawals.py:106](../../python_backend/app/withdrawals.py#L106)。

**复现：**向尚未支付订单发送正确签名、正确金额的退款事件，返回 `409 ORDER_NOT_PAID`，退款被保存为 failed inbox；首次重试延后 30 秒。随后发送支付事件，系统正常结算 100 元利润，代理得到 70 元。退款仍待恢复时，提现申请返回 201，管理员 start 与 confirm 均返回 200。最终重试退款，钱包可用和冻结都为 0，但形成 70 元待追偿。

这不是“退款后已经产生债务仍能付款”的旧问题，而是**退款证据已经被接收、订单及钱包状态尚未反映退款**的窗口。worker 停机或重试退避会延长这个窗口。

**优化：**在订单层统一记录、排序并应用已验证的支付/退款事实；后到 paid 必须在订单锁下检查相关未处理退款。对不能立即确认的退款建立可查询的冻结或待核对状态，阻止相应收益进入新的付款流程。余额为资金池时，应明确保留金额/追偿策略，避免只在 UI 上加提示。不能仅靠缩短 worker 轮询修复。

**验收：**refund → paid、同时到达、失败重试、worker 停机、重复事件均不能释放已知应退款的可支付收益；重复恢复保持幂等。测试可到模拟付款确认，真实渠道另做沙箱验收。

**证据：**[机器结果](evidence/review4-finance.json)，[复现脚本](probes/review4_finance.py)。本次付款回执为模拟值，没有真实转账。

### R4-02 · P1：退出与生成网页登录票据存在会话“续活”竞态

**位置：**[auth.py:73](../../python_backend/app/routers/auth.py#L73)。

**复现：**旧 JWT 先通过依赖鉴权；暂停在票据创建之前；并发 logout 将 token_version 从 0 增到 1，旧 JWT 已返回 401；恢复票据创建后，它重新读取用户并使用最新 version=1，返回票据 200；兑换后新 JWT 访问受保护接口仍返回 200。代理和管理员均复现。

**根因：**鉴权依赖只向后传递 user_id，票据创建重新读取最新版本，没有对照最初获准的会话版本。被撤销的旧身份请求因此获得了新版本身份。

**优化：**传递经过验证的身份上下文（user_id、role、token_version），发票据时在用户行锁内重新校验原始版本并插入票据。logout 使用同一行的版本更新作为串行化边界。旧请求不能自动升级为新会话版本；兑换也保留角色、版本、过期、单次消费检查。

**验收：**针对 agent/admin，分别覆盖“发票据先提交→退出→兑换”和“鉴权先通过→退出→发票据继续”。前者票据兑换失败，后者票据创建失败；正常流程仍可单次兑换。

**证据：**[机器结果](evidence/review4-session-race.json)，[并发探针](probes/review4_session_race.py)。

### R4-03 · P2：对账验证了日志和钱包各自自洽，未核对两者逐笔对应

**位置：**[reconciliation.py:274](../../python_backend/app/reconciliation.py#L274)、[reconciliation.py:315](../../python_backend/app/reconciliation.py#L315)。

**复现：**正常结算 100 元利润后，调用现有钱包服务给无关代理追加该订单的 10 元 commission。未关闭 append-only 触发器。实际 commission movements 合计 110 元、无关代理钱包和收益均为 10 元，但 `reconcile()` 仍返回 `[]`。

**影响：**补单脚本、未来代码回归或错误运维造成额外入账时，对账可能误报零差异。**未证明普通用户可以通过公开 API 给自己加钱。**

**优化：**按订单、账户、commission 类型建立预期分润集合和实际 wallet movements 集合，双向检查额外、缺失、错误收款人和金额；同时比较总额。历史 opening aggregate 必须有明确迁移边界，不能将缺少逐笔历史记录的旧数据全部报成错误。

**验收：**正常订单零差异；错账户、额外、缺失、改金额四类注入都能报出准确订单与账户。将告警送达和认领纳入验收，不能只输出日志。

**证据：**[机器结果](evidence/review4-finance.json)。

### R4-04 · P2：原生小程序提现翻页会被旧请求覆盖

**位置：**[miniprogram/pages/withdrawals/index.js:20](../../miniprogram/pages/withdrawals/index.js#L20)、[index.js:82](../../miniprogram/pages/withdrawals/index.js#L82)。

第 1 页请求未结束时切第 2 页，第 2 页先完成，第 1 页最后返回，代码无请求序号校验，直接覆盖列表和钱包。探针最终 `currentPage=2`，展示的却是 `page-1-record`，余额也回退为旧的 `100.00`。

**优化：**请求携带页面快照与递增序号，只接纳最新请求；页面隐藏/卸载后忽略响应。分页按钮结合 loading 防连点，钱包与账户数据另设刷新职责。

**验收：**反向完成两个请求、快速多次翻页、onShow 与翻页并行，不出现页码/内容错配；失败时保留最后一次成功结果并明确标记。

**证据：**[Node VM 探针](evidence/review4-native-withdrawal-race.cjs)。这是 JavaScript 状态复现，不能代替微信真机验证。

### R4-05 · P2：每分钟自动刷新会重置分页并关闭正在查看的详情

**位置：**[agent-ledger.tsx:136](../../web/components/agent-ledger.tsx#L136)、[admin-mobile-audit.tsx:52](../../web/components/admin-mobile-audit.tsx#L52)、[live-refresh.tsx](../../web/components/live-refresh.tsx)。

revision 变化既触发刷新，也触发 `setPage(1)` 及清空详情选中。用户读到后页、正在核对一笔退款时，会被周期更新打断。静态 demo 关闭了自动刷新，因此在展示网站中不容易发现。

**优化：**区分筛选改变、手动刷新和后台更新。后台更新保留页码、滚动位置与订单 ID，只合并对应数据或显示“有新记录”；只有筛选改变才重置分页。已展开记录变更时给局部更新提示。

**验收：**停留在后页并打开详情超过一个刷新周期，原位置和详情保留，金额更新可识别，键盘焦点不丢失。

### R4-06 · P2：PC 资金页的顶部刷新没有刷新核心审核列表

**位置：**[admin-dashboard.tsx:348](../../web/components/admin-dashboard.tsx#L348)、[admin-dashboard.tsx:540](../../web/components/admin-dashboard.tsx#L540)、[admin-treasury.tsx:85](../../web/components/admin-treasury.tsx#L85)。

顶部刷新更新父级 revision。WalletSummary、AdminOperations 接收刷新信号，但 AdminTreasury 只接收 demo/focus/onComplete，其提现读取依赖自己的 revision/page/status。顶部时间戳更新不代表当前审核列表已更新；付款恢复、账户核验等子模块还各有状态边界。

**优化：**建立明确的资源刷新图：wallet、operations、withdrawals、payment-events、payout-accounts。顶部刷新使当前工作区实际可见资源失效； mutation 后按影响范围刷新。时间戳对应真实资源的最后成功读取，失败时标示“部分更新失败”。可先用统一 hooks/refreshKey 实现，不必为此立即引入大型状态框架。

**验收：**另一个会话新增提现后点顶部刷新，列表和数量一致更新；某子请求失败时，不能全页显示“已更新”。

### R4-07 · P2：局部接口故障会遮挡整个账户下的其他可用页面

**位置：**[agent-context.tsx:98](../../web/components/agent-context.tsx#L98)、[agent-context.tsx:174](../../web/components/agent-context.tsx#L174)、[admin-mobile-context.tsx:122](../../web/components/admin-mobile-context.tsx#L122)。

代理布局将 overview/referral 绑定在一个 Promise.all 中。推广接口 500 也会进入全局 error 分支，将子页面替换为“前往登录”，连明细和提现页面也不显示。老板移动端仅对 team/audit 做例外，overview 失败仍遮挡 treasury。此项根据确定的组件分支确认，本轮没有对正式浏览器注入故障。

**优化：**401/403 才进入身份处理；5xx/超时由资源模块局部降级。缓存的金额可保留，但标注已过期并限制依赖最新状态的提交。推广不可用不应阻断独立的流水读取。

**验收：**分别让 referral、overview、wallet 失败，验证影响范围、局部重试和准确错误文案；不能用重新登录解决所有网络故障。

### R4-08 · P3：PC 工作区缺少 URL 状态，刷新和返回会丢失位置

**位置：**[admin-dashboard.tsx:44](../../web/components/admin-dashboard.tsx#L44)。

四个工作区仅保存在 React 状态中，缺少可恢复的路由或查询参数。审计与资金任务无法得到可复现链接，刷新回资金总览。

**优化与验收：**工作区、筛选、页码和选中订单使用可校验的路由状态；刷新、后退、复制链接后恢复同一任务位置。服务端仍独立检查角色和数据权限，URL 不作为授权凭据。

### R4-09 · P3：错误提示使用正收益绿色，状态语义相互冲突

**位置：**[admin-treasury.tsx:257](../../web/components/admin-treasury.tsx#L257)、[payment-recovery.tsx:95](../../web/components/payment-recovery.tsx#L95)。

两处 error alert 都使用 `var(--positive)`。付款失败、收益成功因此使用同类强调信号，用户需要读完文本才知道是否异常。

**优化与验收：**建立 positive/negative/warning/neutral 状态组件；失败有负向颜色、图标和行动文案，待核验/结果未知用警示语义。退款导致的负收益按符号与业务类型渲染。先保证信息准确，再统一外观。

## 架构与交付评价

### 应当保留

- Python 是实际资金与 API 后端；React/Next 与小程序仍需要 JS/TS。仓库语言比例不能说明后端有没有迁移。
- Decimal 按分处理、单订单行锁、钱包锁顺序与原子更新、订单归属快照、退款冲正和提现认领已有价值。本轮没有发现正常结算重复分钱的新证据。
- Next 的 BFF 有同源、Cookie 与后端代理职责；它与 Python 业务代码同仓不等于职责混写。
- 生成契约、共享展示组件同步和 CI 门禁应继续保留。

### 应当调整

1. **事件处理层：**把订单业务事实与一次通知的处理结果区分开。退款失败 inbox 仍可能代表必须限制付款的有效事实。
2. **身份依赖：**返回完整认证上下文，避免路由通过 user_id 再读取后“继承”新权限或新版本。
3. **资金对账：**逐单从业务分润到实际记账再到钱包余额完整贯通，历史 opening 单独解释。
4. **前端数据层：**统一刷新、取消、版本检查、分页及 stale/error 状态。页面容器负责布局，资源 hooks 负责读取与失效，展示组件不再各自发明刷新协议。
5. **展示与正式验收：**静态 demo 用于视觉和导航；正式应用用于网络时序、权限、错误状态。两套测试目标分别记录。
6. **多端边界：**给 Web、代理原生、老板原生列能力矩阵。当前老板小程序部分能力通过 Web 桥接，必须标清，不以 H5 响应式等同原生交付。

本轮基线提交已包含上次缺失的 Python 模块和依赖约束；“本地有代码但没提交”的旧问题在当前基线不再成立。

## 为什么当前 UI 仍显得普通

### 1. 第一眼强调了历史总额，实际运营任务靠后

1440×900 实测：分润规则区 y≈526，资金待办 y≈713，全网分账审计 y≈895。首屏大段空间被大金额、静态比例和分隔线占据。累计净收益是重要背景数据，但老板日常决策还需要知道可用、冻结、待审核、失败待恢复。

375×812 代理首页中，品牌、页签、余额、快捷入口和身份条依次叠加，“最新分润”标题在约 y=660，首条记录接近底部导航。舒适留白不应靠叠加重复导航产生。

### 2. 字体只写了名字，尚未形成稳定字体交付

[globals.css:4](../../web/app/globals.css#L4) 声明 Geist/Inter，但 [layout.tsx](../../web/app/layout.tsx) 未加载字体，本轮未发现对应字体资产加载。实际字形依赖本机字体和 fallback。不能仅凭 computed font-family 中出现 Geist 就声称 Geist 已加载。

大金额全部粗等宽，会让标题资产数字与订单代码像同一层信息。建议在新规范获准后将 hero 数字改为有等宽数字特性的无衬线字体；订单号、逐笔金额列及精确审计数据保留 mono。此前“所有金额必须 mono”的要求应在实施时明确按本次新规范更新，不能悄悄混用。

### 3. 大面积同色、同权重，靠线条切区域

当前有结构但缺少稳定表面层级。需要背景/容器/浮层三档中性色，少量强调色和清晰文字梯度；大面积发光、每卡不同渐变、更多胶囊不能解决层级问题。

### 4. 金融质感也来自状态可信

刷新是否真的更新、查看详情是否突然关闭、余额是否被旧请求覆盖，都影响可信感。资金页的精致程度必须覆盖 loading、stale、partial-error、empty、disabled、pending、refunded 等状态。

## 更高级的 UI 方案

**推荐老板 PC 采用“专业资金工作台”，代理移动采用“精品财富账户”的层级原则。** 两端共享颜色语义、字体和状态，不强求相同排版密度。

- PC：窄侧导航 + 紧凑顶栏；首屏左侧可用资产和冻结金额，右侧待办；第二层为累计收益/GMV/佣金；第三层为紧凑审计记录。固定分润规则下沉至明细解释。团队图提供按需展开与侧面详情，避免无限长树撑满页面。
- 移动：身份栏压缩；一个清晰资产主卡；两项主操作；简短的今日/历史指标；最近两条流水尽量在首屏出现；底部四 Tab 保持稳定。推广和身份说明进入“我的”。
- 字体：自托管或构建时打包字体；资产数字用 tabular-nums；币种与小数保持可读但弱化；审计列保持准确对齐。
- 材质：石墨背景、铂金文字、三级中性表面；主行动使用少量浅绿；只有确切的正向流入使用收益色。负收益与退款使用文字、图标和颜色共同表达。
- 交互：行 hover、明确焦点、按压反馈、可撤销的筛选；详情关闭后焦点返回触发器；保留浏览上下文；动画短且尊重减少动效设置。
- 内容：不加入无数据依据的折线、月增长百分比或“系统健康”绿点。缺少真实比较周期数据时展示中性口径说明。

完整颜色、尺寸、页面结构和状态验收见 [高阶视觉规范](../design/2026-10-05-premium-fintech-proposal.md)。聊天中的两套设计可切换并展开订单；它们是提案，尚未替换当前站点。

## 复现方式

仅使用可丢弃、数据库名以 `_test` 结尾的 PostgreSQL。测试助手创建独立 schema、运行迁移并在结束后清理；不要连接业务数据库。

在仓库根目录、已设置 `TEST_DATABASE_URL` 后：

```sh
PYTHONPATH=python_backend:python_backend/tests python_backend/.venv/bin/python docs/reviews/probes/review4_finance.py
python_backend/.venv/bin/python docs/reviews/probes/review4_session_race.py
node docs/reviews/evidence/review4-native-withdrawal-race.cjs
```

Python 探针输出 `/tmp/review4-finance-evidence.json`、`/tmp/review4-session-race.json`；本轮原始结果已归档在本文 evidence 目录。探针用于证明当前缺陷，修复后应改写为断言安全结果的正式回归。

**锐评：这个项目现在的短板，既不是 Python 没写，也不是背景不够黑。资金事件和会话的边界仍有真实漏洞，界面则把“金融风格”做得比“金融操作”更突出。先让资金、状态和操作过程可信，再用克制且统一的设计放大这种可信感，才会显得高级。**
